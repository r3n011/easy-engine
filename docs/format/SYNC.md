# 积木 ↔ 场景 双向同步规则

> L1（积木模式）与 L2/L3（场景/引擎模式）看的是**同一份项目**。
> 用户在任一侧改动，另一侧都不能坏。
>
> 这份规则必须和调度器一样早定下来。**晚定 = 返工。**

## 一、先解决一个容易想歪的问题

直觉上会以为"积木说的位置"和"场景里摆的位置"是同一个值，于是要做双向同步。
**不是的。** 两者的语义本来就不同：

| | 是什么 | 例子 |
|---|---|---|
| **场景里的值** | **初始状态**（游戏开始前摆在哪） | 小猫初始在 `(0, 0)` |
| **积木里的值** | **运行时的运算结果** | 「移到 x: `10` y: `20`」 |

所以 `transform.position` 和积木里的 `X=10` **根本不冲突**，它们本来就不是一个东西。

**这个认识决定了整个同步方案**：大部分"看起来要同步"的东西其实不用同步。
真正需要同步的只有**结构**：有哪些角色、有哪些造型、谁引用谁、节点长什么样。

## 二、真正需要同步的清单

| 变更 | 发生侧 | 同步动作 | 会不会打断积木 |
|---|---|---|---|
| 新增角色 | L1 | 在 `nodes` 里加一个节点（默认模板） | 否 |
| 新增角色 | L2 | 同上；若该节点用了积木无法表达的节点类型，标为**不透明单元**（见 §5） | 否 |
| 删除角色 | 任一侧 | 删节点；**引用它的积木不自动删**，标为"悬空引用"并提示 | 断引用，但可一键修复 |
| 改显示名 | 任一侧 | 改 `node.name`。**`node.id` 永不变** | 否 |
| 改造型 / 声音列表 | 任一侧 | 改 `node.costumes` / `node.sounds` | 否 |
| 切换节点模板 | L2 | 改 `node.template`；运行时按新模板重建节点子树 | 否 |
| 改初始坐标 / 大小 / 可见 / 图层 | 任一侧 | 改 `transform` / `visible` / `order` | 否 |
| 加一个积木脚本 | L1 | 追加到 `node.scripts` | — |
| 在 L3 直接写 GDScript | L3 | 存进 `ext.scene.scripts`，L1 里显示为一个**不可展开的代码块** | 否 |
| 加积木表达不了的子节点（材质、着色器、非积木节点） | L2/L3 | 存进 `node.children`，L1 折叠显示 | 否 |

**结论：同步动作几乎全是"改结构字段"，没有一个是"把运行时的值写回去"。**
这就是为什么这套机制可以做得很稳。

## 三、id 稳定性：整件事的地基

```
node.id      一旦生成永不改变，即使改名、改模板
node.name    可以随便改，只影响显示
```

积木通过 **id** 引用角色（`"target": "Player"`），所以改名不会断引用。
删掉再建一个同名角色，它拿到的是**新 id**，老引用会明确报"目标不存在"，
而不是悄悄指到另一个角色上——**宁可报错，也不要静默指错**。

编辑器要做的：删除角色时扫描所有积木，列出受影响的引用并提供
「把引用改到另一个角色」/「删除这些积木」两个选项。

## 四、冲突处理

两个视图可能在不同时间改同一个字段（例如 L2 改了初始坐标，同时 L1 的某个操作也想改）。

规则：**后保存者获胜，但必须让用户知道。**

```jsonc
// project.json 顶层
"revision": 42,
"revisionOwner": "scene"     // 最后一次改动来自哪个视图
```

切档时如果检测到"另一侧有改动且可能冲突"，弹一次提示：

> 场景模式改了「小猫」的初始坐标，积木模式下有 2 处积木可能依赖这个值。
> [查看差异] [以场景为准] [以积木为准]

因为 §1 的原因，真正的硬冲突很少，多数只是"提示一下"。

## 五、不透明单元（Opaque Unit）

L2/L3 能做的事远比积木多。这些内容必须**原样保留**，在 L1 里表现为一个折叠的方块：

```jsonc
{
  "id": "Player",
  "template": "RIGID_BODY_2D",
  "children": [
    {
      "opaque": true,                       // ★ L1 不解析、不修改
      "type": "PointLight2D",
      "properties": { "energy": 1.2, "texture": "res://..." }
    }
  ],
  "ext": {
    "scene": {
      "scripts": ["extends Node2D\nfunc _ready():\n\tpass"],   // L3 直接写的脚本
      "material": { "shader": "res://shaders/outline.gdshader" }
    }
  }
}
```

L1 里的显示：

```
🐱 小猫
   └ 🔒 高级内容（2 项，请在高级模式查看）
```

**绝不能静默丢弃。** 用户从 L1 保存时，`children` 与 `ext` 原样写回
（这正是"未知字段保留"机制在起作用，见 `EE-FORMAT.md §6.2`）。

## 六、Blockly 只是视图，不是数据

这是避免"后期更新痛"的关键决定：

```
.ee / project.json   ←→   Blockly 工作区
    （唯一事实来源）           （纯视图，可随时重建）
```

- **打开项目**：把 §3 的脚本表示法渲染成 Blockly 积木
- **用户编辑**：监听 Blockly 的变更事件，序列化回 §3 表示法
- **绝不把 Blockly 的序列化结果存进 `.ee`**

收益（都是"后期更新"时才体现的）：

| 场景 | 如果存了 Blockly 格式 | 现在 |
|---|---|---|
| Blockly 大版本升级 | 项目文件可能读不出来 | 无影响，只是视图换了 |
| 换掉 Blockly（例如自研积木渲染器） | 全部项目作废 | 只换渲染层 |
| 手写/脚本生成项目 | 不可能 | 直接写 JSON |
| diff / code review | 一坨 id，没法看 | 可读 |

代价是要写一个**双向渲染器**（脚本表示法 ⇄ Blockly 工作区）。这部分工作量是
有界的，而且是编辑器里最值得投入的地方。

## 七、保存流程

```
用户操作（L1 或 L2）
      ↓
只改内存里的原始字典（不重建）
      ↓
revision += 1
      ↓
写回 project.json（未知字段、不透明单元原样带出）
      ↓
IR 缓存打上 sourceHash（§EE-FORMAT §8）
```

**"只改原始字典、不重建"** 是一条铁律：
一旦我们在某处 `Dictionary.new()` 拼一个新对象，未知字段就丢了。

## 八、M1 阶段的验收边界

M1 只做**格式与规则**，不做编辑器 UI。因此本阶段的验收是：

- [x] 节点 / 模板 / 造型 / 声音 / 局部变量的结构定下来（`EE-FORMAT.md §4`）
- [x] 角色引用用 id、id 永不变（`§3.3` 与本文 `§3`）
- [x] 未知字段与不透明单元能往返不丢（加载器不重建字典）
- [x] 脚本表示法与 Blockly 解耦（`EE-FORMAT.md §3`）
- [ ] 双向渲染器（M4 做编辑器时实现）
- [ ] 悬空引用扫描与一键修复 UI（M4）
- [ ] 冲突提示 UI（M4）
