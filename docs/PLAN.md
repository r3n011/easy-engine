# Easy Engine 技术方案（定稿）

> **一句话定位：把 Godot 的能力，用 Scratch 积木的方式暴露出来让人编程。**
>
> 即：积木 = Godot 的可视化编程语言。让只会 Scratch 的人，用熟悉的积木直接指挥 Godot 做出可发布的游戏。
>
> 本文档所有数字均来自 2026-10-17 对本机源码的实际扫描统计，非估算。

---

## 〇、决策记录（已拍板）

| 编号 | 决策点 | 结论 | 影响 |
|---|---|---|---|
| **D1** | 创作端 | **fork `scratch-gui` 自建编辑器** | 编辑器必须开源（GPL-3.0 传染），需接受 |
| **D2** | 执行层 | **原生 IR 解释器**（GDScript → 热点下沉 C++） | 纯原生、可导出全平台、是护城河 |
| **D3** | 平台 | **Windows 桌面优先** | M5 先做 exe 导出 |
| **D4** | 兼容性 | **不追求兼容社区 `.sb3` 项目**。核心任务是**把 Godot 的实现方式改为积木编程** | 工作量从"复刻 Scratch 语义"转为"设计积木 ↔ Godot 映射"，是**大幅减负** |

**D4 是全局性的重新定义。** 原方案假设要跑 Scratch VM 的语义，现在不需要了。这意味着：

- ✅ 不再需要逐条复刻 Scratch 的 12 条语义陷阱（数值转换怪癖、像素级碰撞、fencing、云变量…）
- ✅ 不再被 `.sb3` 格式绑住，可以设计**自己的项目格式**
- ✅ IR 由**我们自己设计**，不必追随 TurboWarp 的 144 种节点
- ⚠️ 但**线程调度语义（yield / warp / clone / broadcast and wait）仍然是必须吃透的核心难点** —— 这是所有积木语言的真正难点，不是积木本身
- ⚠️ 用户零学习成本的承诺，仍然要求核心积木的**行为直觉**与 Scratch 一致（不需要 bit 级一致，但"重复执行"得真的像重复执行）

## 一、竞品与调研结论（决定方案边界）

### 1.1 Gandi IDE 的 GUI **不开源**

枚举 `github.com/orgs/Gandi-IDE/repositories` 全部 23 个仓库，**没有编辑器主仓库**。官方[版权&致谢](https://dev.getgandi.com/acknowledgements)只列出三项开源：虚拟机、扩展、Monaco 编辑器。砍掉创作端 GUI 是 Gandi/Cocrea 的商业边界。

**对我们的意义**：自建编辑器是必然选择（已定 D1），Gandi 的价值变成"**参考资料**"——它的 VM 是 TurboWarp VM 的二次开发，额外提供了 `counter.*` / `gandi.*` / `movegrid` / 全局自制积木 / `ccw_hat_parameter` 等扩展积木，这些是我们设计积木分类时的好素材。

### 1.2 关键参考：TurboWarp 的编译器证明了「积木 → IR → 原生执行」的可行性

`Gandi-IDE/scratch-vm/src/compiler/`（继承自 TurboWarp）：

| 文件 | 行数 | 作用 |
|---|---|---|
| `irgen.js` | 1768 | 积木 → 中间表示 IR |
| `jsgen.js` | 1571 | IR → JavaScript |
| `jsexecute.js` | 636 | IR 解释执行 |
| `intermediate.js` | 115 | IR 结构定义 |

IR 节点形态（**声明式、扁平、可解释**）：

```js
case 'motion_movesteps': return { kind: 'motion.step', steps: ... };
case 'operator_add':     return { kind: 'op.add', left: ..., right: ... };
```

**实测 IR 共 144 种 `kind`。** 这说明"积木 → IR → 原生执行"是一条被工业界验证过的成熟路径，不是发明。

### 1.3 真正的难点在调度器，不在积木

`scratch-vm/src/engine/` 真实行数：

| 模块 | 行数 | 说明 |
|---|---|---|
| `runtime.js` | 3843 | 运行时总控：线程表、事件、广播、克隆体、计时器 |
| `blocks.js` | 1632 | 积木图与 opcode 表 |
| `target.js` | 870 | 角色（相当于我们的"节点模板"） |
| `thread.js` | 522 | **线程状态机：yield / warp / 状态码** |
| `execute.js` | 541 | **积木执行循环：让步点判定** |
| `sequencer.js` | 362 | **主循环：每帧步进所有线程** |
| 其余 engine 文件 | ~1900 | adapter / frame / 资源 / 插值 |
| `blocks/*.js`（138 个核心 opcode） | 2883 | 积木实现 |

→ **`thread.js` + `execute.js` + `sequencer.js` 这 1425 行是"积木语言的灵魂"**。无论是 Scratch、TurboWarp、Gandi 还是我们要做的引擎，都必须解决同一组问题：

1. 每个线程持有一个"积木栈"，每帧执行到**让步点**才暂停
2. **warp 模式**（原子执行）：循环内不让步，直到退出 warp
3. `wait` / `wait until` / `broadcast and wait` / `glide` 的等待语义
4. `stop this script` / `stop other scripts` / `stop all` 的传播规则
5. 克隆体的创建/销毁与局部变量继承

**我们的策略：这套调度语义直接参考/移植 TurboWarp 的设计（MPL-2.0，允许闭源链接使用），积木实现则 100% 自研对接 Godot。** 这样把最大的风险点用成熟设计兜住。

### 1.4 许可证

| 组件 | 实际声明 | 我们的用法 | 风险 |
|---|---|---|---|
| Godot | MIT | 内核基座 | ✅ 可闭源 |
| **`TurboWarp/scratch-gui`** | **GPL-3.0** | fork 做编辑器 | ⚠️ **编辑器必须开源** |
| `TurboWarp/scratch-vm` | MPL-2.0 | 调度器设计参考 | ✅ 文件级 copyleft，闭源链接 OK |
| `TurboWarp/packager` | 见仓库 | 桌面打包参考 | ✅ |
| `Gandi-IDE/scratch-vm` | MPL-2.0 / LGPL-3.0-only / BSD **三处矛盾** | 仅作行为参考 | ⚠️ **不引用其代码**即可规避 |
| `Gandi-IDE/gandi-blocks` | Apache-2.0 | 可选参考 | ✅ |
| `Gandi-IDE/custom-extension` | LGPL-2.1 / 官网称 GPLv3 矛盾 | 不引用 | ⚠️ 规避 |
| `GodotJS/GodotJS` | MIT | 本轮不用 | ✅ |

**结论与策略**：
1. **编辑器开源（GPL-3.0），运行时与云服务自研闭源**。这与 Gandi/Cocrea 的实际做法一致，社区可接受，且编辑器开源本身能带来生态。
2. 调度语义**参考 TurboWarp（MPL-2.0）**，**刻意绕开 Gandi VM**，直接消掉那段许可证矛盾。
3. **商标**：产品名不得使用 "Scratch"（MIT 商标政策）。宣传语可用"兼容 Scratch 积木的使用习惯"。

### 2.2 执行模型：为什么选解释器

| | 解释器（选定） | 代码生成 |
|---|---|---|
| 编辑器内"运行" | 即时、可热改、无需编译 | 每次改动都要重新生成 |
| 调试 | 可断点、可单步、可看线程栈 | 需 source map |
| 性能 | 中等（GDScript），热点可下沉 C++ | 高 |
| 导出 | 直接带 IR + 运行时 | 生成 .tscn + .gd，用户可继续手写 |

**定稿：主路径走解释器。** 代码生成作为后续可选优化（把 IR 生成 GDScript + `.tscn`，让高级用户能"降级"到 Godot 原生工程）——这是很有吸引力的进阶路线，但不进 M1–M5 的关键路径。

### 2.3 IR 设计原则（自研，参考而非照搬）

```gdscript
# 一个 IR 节点
{ "op": "set_property", "target": {"node": "@self"}, "prop": "position:x", "value": {"op":"add", ...} }
{ "op": "call_method",  "target": {"node":"@self"}, "method": "move_and_slide", "args": [] }
{ "op": "await_signal", "target": {"node":"@self"}, "signal": "ready" }
{ "op": "yield_frames", "n": 1 }
{ "op": "warp_begin" } / { "op": "warp_end" }
```

设计要点：
- **扁平、可序列化**：便于缓存与跨进程传输
- **目标统一为"节点引用"**（`@self` / `@stage` / 节点路径 / 变量持有的引用）→ 这是它区别于 Scratch IR 的关键，也是能操作任意 Godot 节点的基础
- **每个节点显式声明让步语义**（是否 yield）

## 三、积木 ↔ Godot 映射设计（本方案的核心）

### 3.1 「角色」不是特殊概念，而是**节点模板**

这是让 Scratcher 零学习成本、同时不牺牲 Godot 能力的**关键设计**：

```
GameRoot (Node2D)                      ← Scratch 的"舞台"
 ├─ @self 节点模板：SPRITE_2D
 │    Node2D "Player"
 │     ├─ Sprite2D          ← 造型/外观/特效
 │     ├─ CollisionShape2D  ← 可选（勾选"参与碰撞"时自动加）
 │     └─ AudioStreamPlayer ← 可选
 └─ @self 节点模板：SPRITE_2D
      Node2D "Enemy" ...
```

- Scratcher 看到的还是"角色 + 造型 + 声音"，行为完全一致
- 但**角色是可换模板的**：`SPRITE_2D`（普通）、`CHARACTER_BODY_2D`（带平台跳跃物理）、`RIGID_BODY_2D`（刚体物理）、`AREA_2D`（触发器）、`CONTROL`（UI）
- 换模板 = 换 Godot 节点类型 = 立刻获得该类型的全部能力
- 高级用户还能**手动编辑节点树**，积木照常工作

### 3.2 核心积木（Scratch 风格 → Godot 实现）

行为直觉与 Scratch 一致，实现落在 Godot 原生对象上：

| 积木 | 目标 Godot 对象 |
|---|---|
| 移动/定位/朝向/旋转样式 | `Node2D.position / rotation / scale` |
| 显示/隐藏/造型切换/大小 | `CanvasItem.visible` / `Sprite2D.texture` / `scale` |
| 图形特效（颜色/鱼眼/旋转/像素化/亮度/虚像） | `CanvasItem.material` 上的 shader uniform |
| 图层前后 | `Node2D.z_index` / 兄弟节点顺序 |
| 播放声音 | `AudioStreamPlayer`（含播放器池与"播完为止"语义） |
| 当绿旗被点击 / 当按键 / 广播 | 自研**信号总线**，不绑死 Godot signal（Scratch 的广播有自己的等待语义） |
| 重复/重复直到/如果/等待/等待直到/克隆体 | 调度器 + 节点实例化 |
| 侦测（碰到/距离/鼠标/按键/计时器/属性） | 物理查询 `PhysicsDirectSpaceState2D` / `Input` / `Time`；**不追求像素级碰撞**（D4），用碰撞形状，观感更好且性能更高 |
| 运算/变量/列表 | 运行时值栈与变量表（克隆体继承语义） |

### 3.3 元积木（通用逃生舱）——**这是"永不缺积木"的保证**

不是为 Godot 的每个 API 手工做积木，而是提供 6 个元积木覆盖几乎全部 API：

| 元积木 | 映射 |
|---|---|
| `[节点] 的 [属性] 设为 (值)` | `Object.set_indexed()` |
| `[节点] 的 [属性]` | `Object.get_indexed()` |
| `调用 [节点] 的 [方法] 参数 (...)` | `Object.callv()` |
| `当 [节点] 发出 [信号]` | `Object.connect()` + 线程启动 |
| `发送 [信号] [参数...] 给 [节点]` | `Object.emit_signal()` |
| `新建 [节点类型] 到 [父节点]` / `从场景 [路径] 实例化` | `ClassDB.instantiate()` / `PackedScene.instantiate()` |

**属性/方法/信号名做成下拉自动补全**（编辑器通过查询 Godot 的 `ClassDB` 生成候选列表），这样老人也能用、高手也不受限。

### 3.4 Godot 能力积木（护城河）

按 M6 逐批交付，每批都是"Scratch 做不到的事"：

| 批次 | 积木组 | 卖点 |
|---|---|---|
| M6.1 | 物理 2D（刚体/碰撞层/冲量/射线检测） | 真实物理 |
| M6.2 | 粒子系统、着色器特效 | 画面质感 |
| M6.3 | TileMap 瓦片地图、关卡编辑 | 做关卡效率 |
| M6.4 | 动画（AnimationPlayer/骨骼）、状态机 | 做角色 |
| M6.5 | 场景切换、存档读档、设置菜单 | 做完整游戏 |
| M6.6 | 相机（跟随/抖动/限制）、手柄、音频总线 | 手感 |
| M6.7 | 联机（Godot 高层多人 API） | 多人游戏 |

### 3.5 坐标系与舞台

| Scratch 习惯 | 实现 |
|---|---|
| 原点在舞台中心，Y 向上 | 舞台根节点做 Y 翻转（`position = center + Vector2(x, -y)`），**对外保持 Scratch 手感** |
| 方向 0=上、90=右（逆时针） | `rotation = deg_to_rad(90 - direction)` |
| 舞台 480×360 | `SubViewport` 默认 480×360，项目设置可切 1920×1080 |
| 大小 100 = 原尺寸 | `scale = size / 100.0` |

### 3.6 项目格式

**自定义 `.ee` 格式**（JSON，就是个 zip 包）：

```json
{
  "formatVersion": 1,
  "stage":   { "size": [480, 360], "background": "..." },
  "nodes":   [ { "id": "Player", "template": "CHARACTER_BODY_2D", "children": [...],
                 "costumes": [...], "sounds": [...], "blocks": {...} } ],
  "globals": { "variables": [...], "lists": [...] },
  "settings":{ "physics": {...}, "input": {...}, "export": {...} }
}
```

- **不采用 Scratch 的 `project.json`**：它的结构为 Scratch 的怪癖服务，会束缚我们（例如把"节点树"硬塞进 `targets` 会很难看）
- **但保留一个 `.sb3` 导入器** —— 把 Scratch 的角色/造型/声音/积木转成我们的节点模板，这是吸收存量用户的钩子。放在 M7，不进关键路径

## 四、编辑器 UI 简化设计

### 4.1 问题：Godot 编辑器对 Scratcher 是劝退的

一个只学过 Scratch 的人打开 Godot，会依次撞上这些墙：

| 他看到的 | 他脑子里的声音 |
|---|---|
| 顶栏 20+ 个工作区（2D / 3D / Script / Game / AssetLib / Movie…） | 「这些是什么？我该点哪个？」 |
| 「场景树」「检查器」「文件系统」「节点」四个面板 | 「我只想放一个角色啊」 |
| 右键 →「添加节点」→ 弹出 700+ 个节点类 | 「精灵2D 和 角色身体2D 有什么区别？」 |
| 「属性」「资源」「材质」「着色器」「导出预设」 | 一整套陌生的词汇体系 |
| 一个空场景 | 「我的角色在哪？」 |

**我们已经把界面 100% 汉化，但这只解决了"看不懂英文"，没解决"看不懂概念"。** Godot 的 UI 结构本身是为程序员准备的。

**结论：简易模式不能是"被裁剪过的 Godot 编辑器"，而应该是"另一个以积木为中心的界面"，Godot 编辑器作为进阶形态存在。**

### 4.2 设计原则：分层，而不是隐藏

1. **不做"阉割版 Godot"。** 藏面板会让用户觉得"功能被砍了"，还会踩到"想用却找不到"的坑。
2. **两种视图，同一份项目。** 简单模式与高级模式打开的是同一份数据；随时可升可降，**降级回来不丢东西**。
3. **判断标准**：任何功能，在简单模式里要么有等价入口，要么有一条明确的"去高级模式"的路。

### 4.3 三档模式

| 档位 | 面向 | 界面 | 出现的概念 |
|---|---|---|---|
| **L1 积木模式**（默认） | 只会 Scratch 的人 | 积木编辑器 | 角色 / 造型 / 声音 / 积木 / 舞台 |
| **L2 场景模式** | 想调关卡和属性的进阶用户 | 积木编辑器 + 场景视图 | 角色 = 节点，出现节点树与属性表单 |
| **L3 引擎模式** | 想做复杂项目的用户 | 我们构建的、已汉化的 Godot 编辑器 | Godot 原貌（可选脚本） |

档位开关放在右上角，切档时给的是"你会看到更多东西"的提示，而不是警告。

### 4.4 L1 简单模式的界面

```
┌──────────────────────────────────────────────────────────────────┐
│ [绿旗 ▶] [停止 ■]      项目名                    舞台 480×360     │ ← 只留运行控制
├──────────┬───────────────────────────────────┬───────────────────┤
```

与 Scratch 相比只有两点差异，而且都是**升级**：
1. 舞台是**真 Godot 渲染**的，画面效果远超 Scratch
2. 多了一个「**Godot 能力**」积木分类（物理 / 粒子 / 着色器 / 瓦片地图…）

### 4.5 必须清理的 Godot 遗留痕迹

即使用户大部分时间待在 L1，仍会有 Godot 的痕迹漏出来，这些必须处理：

| 项目 | 问题 | 处理 |
|---|---|---|
| 启动画面 | 默认 Godot logo | 换成 Easy Engine 品牌（`boot_splash` 设置） |
| 项目选择器 | 用户不该看到 Godot 的项目管理器 | 由 Easy Engine 自己的启动器接管 |
| **报错信息** | **2597 条英文硬编码报错**（见 [汉化报告](汉化报告.md)） | 汉化 + **人话化**（改成面向小孩的措辞） |
| 检查器属性名 | 直接暴露 `Sprite2D` / `CharacterBody2D` 等类名 | L2 用**属性表单**代替原始属性列表 |
| 3D 工作区 | 对新手纯噪音 | L1/L2 不出现 |
| 「导出」菜单 | 术语与流程都太专业 | 换成「🚀 **发布游戏**」向导（Windows / Android / Web） |
| GDExtension / AssetLib / 着色器编辑器 | 噪音 | 仅 L3 出现 |
| 编辑器字体 | 依赖系统 `Noto Sans CJK`，Windows 上会退化 | 打包思源黑体子集 |

### 4.6 实现路径

| 方案 | 做法 | 优点 | 缺点 |
|---|---|---|---|
| **A. 自研外壳**（推荐） | 不碰 Godot 编辑器 UI，自建以积木为中心的应用（fork scratch-gui + Godot 运行时进程） | 体验完全可控；Godot 升级不影响我们 | 编辑器要自己写 |
| B. 裁剪 Godot 源码 | 改 Godot 编辑器：删面板、加档位开关 | 复用 Godot 编辑器全部能力 | 每次升级 Godot 都要重新改，长期成本高 |
| C. 做编辑器插件 | 用 `EditorFeatureProfile` 禁用功能 + 加自定义面板 | 改动最小 | 藏不住主布局，做不到"看起来不像 Godot" |

**推荐 A + C 组合**：

- **L1 / L2 = A**：自研积木编辑器，用户**根本不会看到 Godot**（这是把 Scratch 用户接进来的关键）
- **L3 = C**：在已汉化的 Godot 编辑器里装一个 Easy Engine 插件，提供「回到积木模式」「发布游戏」等入口，并把常见操作一键化

> 这条决定会反过来影响路线图的 M4：原计划 M4 是"fork scratch-gui 做编辑器"，现在明确 —— **那个编辑器就是 L1/L2 的全部**，Godot 编辑器只在 L3 出现。

### 4.7 关键机制：两种视图如何共享项目

同一份项目里有两层数据，**角色与节点一一对应**：

```
project.ee/
├── blocks/            积木图（Blockly 序列化）        ← L1 的主数据
├── scene.tscn         Godot 场景（节点树 + 属性）      ← L2 / L3 的主数据
├── assets/            造型 / 声音 / 字体
└── project.godot      Godot 项目配置
```

**双向同步规则**：
- 积木改了属性 → 写回 `scene.tscn` 对应节点
- 在 L2 直接改了属性 → 更新积木里的对应常量
- 冲突以"最近修改"为准

> ⚠️ 这条同步机制是 L1/L2 的核心，**必须和调度器一样早设计**，否则后期返工代价极高。建议放进 M1（数据模型）一起定稿。

### 6.3 本次解决的两个环境陷阱

**陷阱 1：系统 `vswhere.exe` 损坏 → SCons 找不到 MSVC**

- 现象：`ERROR: No valid compilers found, use MINGW_PREFIX...`（Godot 错误回落到 MinGW）
- 根因：`C:\Program Files (x86)\Microsoft Visual Studio\Installer\vswhere.exe` 损坏无法执行；SCons 的 `_VSWHERE_EXEGROUP_MSVS` 只取第一个路径且不校验可用性，永不回退
- 解决（无需管理员）：`C:\Users\Admin\.scons\vswhere.exe` + `…\site_scons\site_init.py` 以高优先级注册
- 验证：`Using Visual Studio 14.3 with Windows SDK 10.0.26100.0.` ✅
- 复现脚本：`tools\setup-vswhere.ps1`

**陷阱 2：Godot 可选依赖下载超时**（`WinError 10060`）

- 仅影响 AccessKit（屏幕阅读器）与 D3D12 后端；OpenGL/Vulkan 不受影响
- 处理：构建参数加 `accesskit=no d3d12=no`；要启用需配置代理

### 6.4 常用命令
