# Godot 4.7.2 完全汉化报告

> 结论先行：**Godot 4.7.2 的简体中文界面官方本来就基本是完整的。我实测出并补掉了真正漏翻的 98 条，界面上会蹦英文的文案已全部清零。** 但"完全汉化"还有两个更深的坑（下面的发现 2 和 3）。

---

## 一、实测数据（改动前）

用真实解析器扫描 `editor/translations/`：

| 文件 | 条目 | 完成度 |
|---|---|---|
| `editor/editor/zh_Hans.po`（编辑器界面） | 6420 | **100%** |
| `editor/properties/zh_Hans.po`（属性/分组名） | 4300 | **100%** |
| `editor/extractable/zh_Hans.po`（导出项目用） | 73 | **100%** |
| `doc/translations/zh_Hans.po`（类文档） | 24056 | **100%** |

**光看这个表会得出"不用干活了"的错误结论**——因为 Weblate 的工作流只把**已翻译**的条目推进仓库，所以"文件里 0 条未翻译"≠"界面 100% 汉化"。真正的口径是：

> 从源码里抽出的**所有可翻译文案**，能否在 .po 里找到**键（上下文 + 原文）完全匹配**的条目。

### 权威口径：源码 ↔ .po 差集

我写了 `tools/extract-ttr.py`，按 `core/string/ustring.h` 的真实签名抽取全部翻译入口：

```cpp
String TTR (const String &p_text, const String &p_context = "");   // 编辑器文案
String TTRN(const String &p_text, const String &p_text_plural, int p_n, const String &p_context = "");
String RTR (const String &p_text, const String &p_context = "");
#define ETR (p_text, p_context)     // 导出项目里用的文案 -> extractable/*.po
#define PNAME(m_value) (m_value)   // 属性名   -> properties/*.po
#define GNAME(m_value, m_prefix)   // 分组名   -> properties/*.po
```

扫描结果：

| 项目 | 数量 |
|---|---|
| 源码中可翻译文案调用（去掉注释后） | **9593** |
| .po 中已有条目（三文件去重） | 10937 |
| **键不匹配（即界面上会显示英文）** | **98** |
| 其中：内部标识符（上游刻意不翻，属正常） | 344 |

## 三、三个关键发现

### 发现 1：上下文是**精确匹配**的，没有回退

`core/string/translation.cpp`：

```cpp
StringName Translation::get_message(const StringName &p_src_text, const StringName &p_context) const {
    const Vector<StringName> *msgstrs = translation_map.getptr({ p_context, p_src_text });
    if (msgstrs == nullptr) {
        return StringName();   // 找不到 → 回退显示英文原文
    }
    ...
}
```

键是 `MessageKey{msgctxt, msgid}`，**上下文对不上就等于没翻译**。

这带来两个后果：

1. 我的分析器最初漏处理 `msgctxt`，把上下文错位绑到了上一条，凭空造出 29 条"假漏翻"（`Spring`、`Mirrored`、`Tabs`、`Clip End`、`Joypad Axes` 等，其实早就有正确译文）。**修好解析器后这 29 条自动消失**——这也是为什么我对 `msgctxt` 的处理要单独写测试。
2. 上游确实存在"源码写了上下文、.po 没同步"的情况（维护版常见），这类字符串在中文界面里会漏出英文。

### 发现 2：**2597 条写死的报错/警告文本，永远无法翻译** ← 真正的"不完全汉化"

界面文案走 `.po`，但引擎的报错是硬编码的。扫描 `ERR_PRINT` / `WARN_PRINT` / `print_error` / `ERR_FAIL_MSG` 等宏：

| 类别 | 条数 |
|---|---|
| `ERR_FAIL_COND_MSG` | 1189 |
| `WARN_PRINT` | 497 |
| `ERR_PRINT` | 491 |
| `ERR_FAIL_MSG` | 237 |
| `ERR_FAIL_NULL_MSG` | 156 |
| `print_error` | 27 |
| **合计** | **2597** |

按模块分布：`scene` 605、`modules` 491、`servers` 379、`editor` 315、`drivers` 305、`core` 264、`platform` 227。

**这才是"中文界面里蹦英文"的主要来源。** 对一个面向中文学习者的产品，小孩写错代码时看到一堆英文报错，体验是断裂的。

要汉化它们，只有三条路：
- **A. 改源码**：给这 2597 处套上 `TTR()`，再走翻译流程。工作量大但彻底，且可以只用 LLM 批量处理 + 人工抽检。
- **B. 运行时拦截**：在 `OS::print_error` / `print` 层做一层英文→中文的映射字典。改动小、可热更新，但只能覆盖"整句固定"的报错（带变量的句子要做模板匹配）。
- **C. 编辑器内展示层做包装**：只在编辑器输出面板做翻译，不改引擎语义。

> 建议：**A 为主 + B 兜底**。这是独立于"界面汉化"的一个子项目，建议单独立项。

### 发现 3：中文字体依赖系统字体，Windows 上会退化

`editor/themes/editor_fonts.cpp` 是这样找中文字体的：

```cpp
if (locale.begins_with("zh") && (locale.contains("Hans") || ...)) {
    var_suffix = { "SC", "TC", "HK", "KR", "JP" };
}
...
noto_cjk_path = OS::get_singleton()->get_system_font_path("Noto Sans CJK " + var_suffix[i], 400, 100);
```

它只认 **`Noto Sans CJK SC`** 这个家族名。而 Windows 上装的中文字体通常叫 **`Noto Sans SC`**（不带 "CJK"），匹配不上，于是退回**内置的 `DroidSansFallback`**——

- 能显示中文（不会变方块，这点已验证）
- 但字形老旧、字重单一、覆盖率有限（GB2312 级别）

**顺带发现一个上游 bug**（`editor_fonts.cpp` 第 182-185 行）：

```cpp
} else if (locale.begins_with("ko")) {
    var_suffix = { "KR", "HK", "SC", "TC", "JP" };
} else if (locale.begins_with("ko")) {   // ← 本该是 "ja"，复制粘贴漏改
    var_suffix = { "JP", "HK", "KR", "SC", "TC" };
}
```

日语分支永远进不去。不影响中文，但说明这段逻辑很脆弱。

**建议**：让这段查找除了 `Noto Sans CJK <变体>`，再依次尝试 `Noto Sans <变体>`、`Source Han Sans <变体>`、`Microsoft YaHei` / `Microsoft JhengHei` 等系统常见家族名；或者干脆**随引擎打包一份思源黑体子集**，彻底摆脱对系统字体的依赖（对游戏产品的可预期性最好）。

## 五、复现步骤

```powershell
# 1) 分析当前缺口
python tools\extract-ttr.py engine\godot      # 权威差集
python tools\zh-todo.py engine\godot          # 筛出真·界面文案

# 2) 回填翻译（已存在会自动跳过）
python tools\zh-apply.py --dry-run            # 预演
python tools\zh-apply.py                      # 写入
python tools\zh-apply.py --hant               # 需要繁体时（注意：现有译文是简体）

# 3) 重新编译（gen.cpp 由 .po 在构建时重新生成）
cd engine\godot
python -m SCons platform=windows target=editor arch=x86_64 accesskit=no d3d12=no -j15

# 4) 截图验证
powershell -File ..\..\tools\screenshot.ps1 -Exe bin\godot.windows.editor.x86_64.exe -Out ..\..\docs\shot.png

# 5) 也可用命令行强制指定语言启动
bin\godot.windows.editor.x86_64.exe -l zh_Hans
```

> 翻译是在**构建时**从 `.po` 生成 `editor_translations.gen.cpp` 打进二进制的（`SCsub` 里 glob 了 `editor/translations/editor/*`），所以改完 `.po` 必须重新编译。

## 六、第二批：枚举标签（快速设置里的英文从哪来）

### 6.1 现象与根因

用户反馈：快速设置对话框里，左侧标签是中文，但**下拉值是英文**——
`Auto (Chinese (Simplified Han))` / `Modern` / `Default` / `Auto (100%)` / `Offline` / `Auto (Stable)` / `kebab-case`。

这不是漏翻，是**代码的设计缺陷**。`quick_settings_dialog.cpp` 把属性的 `hint_string`（枚举值）**同时当成显示标签和序列化值**：

```cpp
editor_styles = pi.hint_string.split(",");        // 值来自属性提示串
style_option_button->add_item(style_value, i);    // 直接当标签显示

void QuickSettingsDialog::_style_selected(int p_id) {
    const String selected_style = style_option_button->get_item_text(p_id);  // 从标签取值
    _set_setting_value("interface/theme/style", selected_style);             // 写回配置
}
```

**翻译了标签，写回配置的就会变成「现代」而不是 `Modern`，设置直接坏掉。** 所以作者用
`set_auto_translate_mode(AUTO_TRANSLATE_MODE_DISABLED)` 主动关掉了自动翻译。

### 6.2 范围比想象的大：检查器里所有枚举都是英文

```cpp
// editor/inspector/editor_properties.cpp
void EditorPropertyEnum::setup(const Vector<String> &p_options) {
    ...
    options->add_item(String(", ").join(K.value));   // ← 没有 TTR
}
```

扫描全引擎 `PROPERTY_HINT_ENUM`：

| 项目 | 数量 |
|---|---|
| 含枚举的属性定义 | 725 处 |
| 涉及文件 | 195 个 |
| **唯一枚举标签** | **1165** |
| 标签出现总次数 | 2588 |

也就是说**旋转模式、处理模式、纹理过滤、材质混合模式……所有枚举下拉框都是英文的**。

### 6.3 已修：把「标签」和「值」分开

**代码改动**（`quick_settings_dialog.cpp`）：

```cpp
// 显示用译文，回写用原始值
style_option_button->add_item(TTR(style_value, "Editor Theme Style"), i);
style_option_button->set_item_metadata(i, style_value);

void QuickSettingsDialog::_style_selected(int p_id) {
    _set_setting_value("interface/theme/style", style_option_button->get_item_metadata(p_id));
}
```

`Display Scale` 的 `Auto (125%)` 百分比随机器而变，无法作为固定 msgid，用一个取值函数处理：

```cpp
static String _tr_auto_label(const String &p_value, const String &p_context) {
    if (p_value.begins_with("Auto (")) {
        return vformat(TTR("Auto (%s)"), p_value.substr(6, p_value.length() - 7));
    }
    return TTR(p_value, p_context);
}
```

另在 `editor_settings.cpp` 把语言项的 `Auto (%s)` 前缀也接上翻译。

**译文**：新增 24 条（款式 2 / 颜色预设 10 / 显示缩放 1 / 网络模式 2 / 检查更新 4 / 目录命名 2 / `Auto (%s)` 1，另加预览版 1、常规 1），全部带上下文以避开 `Default`、`Auto` 这类高频词。

### 6.4 顺带产出一个**可复现的验证方式**

GUI 自动化在 Windows 上很难稳定（前台窗口锁会吃掉第一次点击），所以改成**离屏验证**：
Godot 把 `.po` 注册为资源加载器，`Translation.get_message(msgid, context)` 也暴露给了脚本，
于是可以直接断言查找结果。

```powershell
godot.windows.editor.x86_64.exe --headless --path tools/verify-translation --script verify.gd
```

```
  OK   [Editor Theme Style] Modern  ->  现代
  OK   [Network Mode] Offline  ->  离线
  OK   [Check for Updates] Auto (Stable)  ->  自动（稳定版）
  OK   [编辑器主题样式] Modern  ->            ← 上下文不一致时查不到，验证"精确匹配无回退"
通过 19，失败 0
```

这套方式同样**兜住了我自己之前犯的 `msgctxt` 解析 bug**——比截图可靠得多。

> ⚠️ 注意：`editor/translations/*/` 目录会被构建系统 `Glob("*")` 全量扫入，**备份文件（`*.bak`）放进去会导致生成非法 C++ 标识符而编译失败**。备份请放到仓库根目录的 `backup/`。

## 七、还没做的（需要你决定）

1. **1165 个枚举标签**（检查器里所有下拉框）要不要全量汉化？机制已通（`EditorPropertyEnum::setup` 加 `TTR` 即可），但量大，建议做成批量任务 + 抽检。
2. **2597 条硬编码报错文本**是否要汉化？建议单独立项，走"改源码 + 运行时兜底"双路。对面向小孩的产品，这个优先级可能比枚举更高。
3. **是否换掉中文字体**？建议打包思源黑体子集，摆脱系统字体依赖。
4. **繁体（zh_Hant）**要不要一起做？`zh_Hant.po` 现为 5903 条，同样有若干键不匹配项；需要一份独立的繁体检修。
