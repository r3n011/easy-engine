# M2 工作清单与验收结果

> 目标：**调度器跑通纯逻辑项目，且让步与 warp 行为正确。**
> M2 是整个项目里最不能返工的一块：语义一旦定错，后面所有积木、所有项目都跟着错。

## 一、交付物

| 文件 | 作用 |
|---|---|
| `runtime/ee/runtime.gd` | 调度器：线程表、帧循环、广播、克隆体、变量、计时器 |
| `runtime/ee/thread.gd` | 线程：**显式帧栈** + 状态机 + warp 深度 |
| `runtime/ee/op_context.gd` | op 与调度器之间唯一的接口（控制流/让步都经它实现） |
| `runtime/ee/values.gd` | 值语义唯一来源：转换、比较、运算 |
| `runtime/ee/expr.gd` | **逃生舱①**：受限表达式的词法/语法/求值 |
| `runtime/ee/target.gd` | 目标（角色与克隆体） |
| `runtime/ee/bridge/node_bridge.gd` | 节点桥：op 与真实 Godot 节点之间的隔层（M2 用无渲染实现） |
| `runtime/ee/providers/core_ops.gd` | 核心 op 的 84 个实现（**含控制流**） |
| `runtime/ee/providers/physics2d_ops.gd` | 扩展示范：物理 op 的实现 |
| `runtime/tests/m2_tests.gd` | **84 项测试** |
| `docs/format/EE-SCHEDULER.md` | 调度语义规范（定稿） |

## 三、被测试钉死的语义

这些是"定错了就要全盘返工"的东西，每一项都有对应测试：

| 语义 | 测试断言 |
|---|---|
| **循环每轮让步** | `重复 3 次` 第 1 帧计数=1、第 2 帧=2、第 3 帧=3 |
| **warp 内不让步** | `warp { 重复 100 次 }` 一帧跑完 |
| **等待 0 秒也让出一帧** | 让出后下一帧才继续 |
| **等待按执行时刻计时** | `wait 0.5` 在第 1 帧（now=0.1）执行 → now=0.6 恢复 |
| **等待直到每帧重算条件** | 条件成立的那一帧就继续 |
| **帧内新线程下一帧才跑** | 广播后 A 先完成，接收方下一帧才覆盖 |
| **广播并等待** | 广播方一直等到接收方全部结束 |
| **克隆体局部变量是副本** | 克隆体改成 2，原型仍是 3 |
| **克隆体数量上限** | 超限时记告警并忽略，不崩 |
| **变量 auto 作用域** | 同名局部变量被写、全局同名不受影响 |
| **方向语义 0=上 90=右** | 朝右走 10 → x=10；朝上走 10 → y=-10 |
| **碰边反弹左右墙公式** | 90 → 270（竖直墙反射是取反，不是 180-d） |
| **停止当前/其他/全部** | 停止后线程表清空且不再执行 |
| **值语义** | `"10" > "9"` 为真、`"abc"+4`="abc4"、除以零得 Infinity |
| **表达式（逃生舱①）** | 优先级、右结合的 `^`、函数白名单、错误定位 |
| **扩展 op 可用** | 物理 op 正常执行；未启用时**报错并指明扩展名** |
| **未知 op 的失败方式** | 记运行时错误，不崩 |

## 四、几个刻意的设计决定

### 1. 不用协程，用显式帧栈

协程做不到「从外部打断一个正在等待的脚本」，而这正是
「停止这个脚本」「停止该角色的其他脚本」「删除克隆体」必需的。
所以线程就是一个可检查、可杀死的数据结构。

### 2. 控制流不在调度器里

`repeat / if / while / warp` 都是 **core provider 里的普通 op**，
通过 `ctx.push_loop()` 操作线程。调度器只做"取下一个 op → 交给 provider"。

代价是多一层间接；收益是**扩展可以写自己的控制流和挂起语义**，
不需要改调度器一行。

### 3. 保护阈值而不是崩溃

| 保护 | 阈值 | 行为 |
|---|---|---|
| warp 超时 | 0.5s | 强制让步（对应 Scratch 的 warp timer） |
| 单帧 op 预算 | 200 万 | 强制让步 + 告警 |

用户写死循环时，程序不该卡死，也不该毫无提示。

### 4. 启动就校验"op 有没有实现"

`verify_providers()` 在启动时检查每个声明的 op 是否有对应方法。
第一次跑就抓出了 3 个我声明了却没实现的孤儿 op。
**在启动时暴露是一行提示，在运行时暴露是一个线上崩溃。**

### 5. 引用环必须显式打断

`Thread.target` 与 `Target.threads` 互相强引用，GDScript 的 RefCounted
没有环回收。测试跑到最后报 199 个对象泄漏——加了 `Runtime.dispose()` 后归零。
编辑器反复预览项目时，这个泄漏会累积。

## 五、M2 的边界（明确没做的）

| 没做 | 原因 / 什么时候做 |
|---|---|
| 真实渲染 | M3 换掉 `node_bridge` 的实现即可，调度器与 op 不动 |
| 「执行代码」真正执行 | 现在会**明确告警**"当前环境不支持"并记录内容，不是静默忽略。M3 用 GDScript 动态实例实现 |
| `碰到 X` 的真实判定 | 桥在无渲染环境恒返回 false；M3 接物理/像素判定 |
| 自制积木（有参数、有返回值） | M3 |
| 计时器的帧率独立性 | 现在按传入 delta 推进；M3 接 `SceneTree` 的真实帧时间 |

## 六、下一步（M3）要接的契约

- 只换 `NodeBridge` 的实现，**不要动** `runtime.gd` / `thread.gd` / `values.gd`
- `yields` 语义、帧内新线程时机、克隆体局部变量副本、变量 auto 作用域——**都别改**
- 实现「执行代码」积木（逃生舱②）
- 自制积木与返回值
- 把 `docs/format/EE-SCHEDULER.md §13` 的契约清单当作回归清单
